## 결론

- 조회 혼합 부하: 80 RPS를 두 번 측정해 p95 64.15ms / 64.39ms, 오류·429·미전송 모두 0건.

- 로컬 기준 여유 있는 조회 구간은 80 RPS 부근으로 관찰했으며, 운영 EC2 최대 처리량이나 동시 사용자 수로 환산하지 않음.

## 자원과 느린 조회

- 서버/DB/Redis는 코어 0,1을 공유하고 k6는 코어 2,3을 사용했다. 다른 Docker 컨테이너 13개는 측정 중 중지했다.
- 백엔드 768MiB / MySQL 512MiB / Redis 128MiB. DB 연결 풀 5, Tomcat 스레드 50.
- 100 RPS 측정 중 수동 표본에서 k6 CPU 13.51%, 백엔드 39.44%, MySQL 147.07%였다. Docker CPU 100%는 코어 하나에 해당한다. 이는 한 시점의 표본이며 기간 평균은 아니다.
- 인기순 목록이 상대적으로 느렸다. 같은 형태의 정렬 쿼리를 테스트 DB에서 EXPLAIN ANALYZE한 결과, 게시글 5,000개를 스캔하며 공감 수 하위 쿼리를 5,000번 평가한 뒤 20개를 정렬했다. 단독 실행 약 26.4ms. 실제 Hibernate 전체 쿼리/동시 부하의 실행 계획과는 구분한다.
- 다음 개선 후보는 인기순 정렬의 공감 수 집계 비용이다. 이번에는 조회 쿼리 최적화를 적용하지 않았으며 성능 개선 전후 수치를 주장하지 않는다.

## 요청 제한 조정

| 항목 | 이전 | 로컬 코드 조정 | 근거 |
|---|---:|---:|---|
| 계정별 조회 | 분당 120 | 유지 | 개인의 과도한 요청 차단 유지 |
| IP별 조회 | 분당 300 | 분당 600 | 공유 IP에서 30명이 12회씩 탐색하는 요청 수용. 지속 허용량 10회/초는 관찰한 여유 구간 80 RPS보다 낮음 |
| 계정별 분석 | 분당 1 | 유지 | 실제 외부 API 한도를 측정하지 않았음 |
| IP별 분석 | 분당 10 | 유지 | 동일 |

600은 검증된 운영 최적값이 아닌 보수적인 초기 정책이다. 현재 토큰 버킷은 분당 충전량과 최대 버스트 용량이 같으므로 IP 한도를 올리면 즉시 허용할 수 있는 요청 수도 늘어난다. 여러 IP의 전체 합산 부하를 600으로 제한하는 설정은 아니다. 운영에서는 정상 사용의 429 발생률과 서버 자원을 보고 조정해야 한다.

제한 재활성화 후 실제 HTTP 검증:

- 한 계정 과다 조회: 200 응답 122건, 429 응답 58건. 시간 경과 중 충전되므로 단순한 120건 고정 창과 다르다.
- 동일 IP의 30계정 × 12회 정상 탐색: 360건 모두 통과. 이후 초과 요청 1,000건 중 307건 허용, 693건은 429. 거절 응답 Retry-After도 검증.
- 같은 계정의 연속 분석: 첫 요청 200, 두 번째 요청 429.

## 검증과 배포 상태

- 기존 300 상한에서 학교 공유 IP 회귀 테스트 실패를 확인한 후 600으로 변경해 통과시켰다.
- 백엔드 전체 185개 테스트 통과, 결과 집계 단위 테스트 4개 통과, 운영 스크립트 단위 테스트 11개 통과.
- 미전송을 성공으로 허용하도록 집계 조건을 변형하면 테스트가 실패함을 확인하고 원복했다.
- 운영 bootJar와 loadTestJar 빌드 통과. app.jar에 loadtest 클래스/프로필이 없음을 ZIP 내용으로 검증했다.
- k6에 운영 도메인을 명시하면 init 단계에서 거부해 HTTP 요청을 시작하지 않는다.
- 프론트 코드와 DB 마이그레이션은 변경하지 않았다. 운영 서버 반영·커밋·푸시는 수행하지 않았다.

원본 JSON·CPU/메모리 표본·로그·테스트 JWT는 `results/`에 보관하며 Git에서 제외한다. 이 문서에는 요약값만 포함한다.

- 추가 확인: 실제 MySQL 마이그레이션 검사 5개 통과. 테스트 컨테이너는 종료하고, 측정 중 중지했던 기존 컨테이너 13개는 다시 실행했다.
